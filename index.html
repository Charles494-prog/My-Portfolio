    Chapter 4

    How I build

    Every project is a small adventure, and I take the same route every time. It isn’t a straight line. It’s a cycle.

    1. Stage 1 · The call

      Listen & gather requirements

      I sit with the people who do the work, watch where they repeat themselves, ask what slows them down, and write down every rule in their own words.

      Comes outClear requirements and the real rules behind them.

    2. Stage 2 · The map

      Plan the route

      I break the work into small pieces I can finish and show, decide what matters most, and list the risks before they become problems.

      Comes outA prioritized plan with small, deliverable steps.

    3. Stage 3 · The blueprint

      Design the data, screens & security

      Database first, because good data makes everything else simple. Then the screens and the flow between them, with roles and security planned from day one.

      Comes outA data model, screen layouts and access rules.

    4. Stage 4 · The forge

      Build the backend, with tests alongside

      I write the server logic in small steps, and each step gets its unit and feature tests right away, not at the end. The tests become a safety net that grows with the system.

      Comes outA working backend already protected by tests.

    5. Stage 5 · The craft

      Build the frontend, and test it too

      I turn the design into screens people actually enjoy using: fast, clear, and checked on phones and laptops, in light and dark mode.

      Comes outEasy-to-use screens wired to the backend.

    6. Stage 6 · The trial

      Test everything, together

      The boss battle: the full automated suite (about 500 tests), a click-through of every flow in a real browser, and a run on a staging copy of the real data, all before anyone relies on it.

      Comes outProof that it works, not just a feeling.

    7. Stage 7 · The launch

      Deploy safely

      Back up the database first, apply the changes, and release with a one-click launcher, always with a way back if something goes wrong.

      Comes outA live system, with no data lost.

    8. Stage 8 · The campfire

      Listen again & maintain

      I watch how people really use it, read the logs, fix what hurts, and collect the next ideas. Their feedback becomes the next set of requirements.

      Comes outThe next quest.

    And the cycle starts again, a little wiser each time.

    The engineering under the hood of the systems on this page. Each item has the technical term and what it means in plain words.

    ◆ Systems architecture

    • Laravel 12 MVC + service layerBusiness rules live in focused service classes (report builders, exporters, eligibility, security policy), not in controllers.
    • Shared Rust coreOne library powers both the Windows app and the Android app, so the same input always gives the same documents.
    • Embedded HTTP server + WebViewThe desktop app is a single .exe that runs its own local web server and shows it in a native window.
    • LAN team modeOne PC hosts the system and every staff computer on the office network uses it at the same time.

    ⚡ Real-time & async

    • Laravel Reverb (WebSockets)Live chat, read receipts, typing indicators and a live task feed, pushed instantly with broadcast events.
    • Laravel Echo + pusher-jsThe browser side that listens for those events.
    • Queue workers + schedulerBackground work runs outside the request: daily cleanup and an automatic monthly backup.
    • async / await, threadsNon-blocking requests in the browser; in Rust, slow work (like Android’s save dialog) runs on its own thread.

    ▤ Database design & optimization

    • MariaDB · migrations onlyEvery schema change is a versioned migration, so any PC can be rebuilt to the exact same structure.
    • Indexes, unique keys, foreign keys~100 constraints and lookup indexes keep searches fast and data consistent.
    • Lean queriesSelect only the columns needed, paginate long lists, and load reference data once per request.
    • History & audit tablesEvery record change is logged; earlier reasons and snapshots are kept, never overwritten.
    • Files stored in chunksUploaded files are also saved in the database in pieces, so one backup restores everything on another PC.

    ⇄ Concurrency & data integrity

    • Transactions + row-level locks~40 critical writes run inside transactions with lockForUpdate, so two people editing at once never collide.
    • Stale-data checksBefore saving, the server confirms the list hasn’t changed since the user opened it.
    • Undo with state checksSession changes can be undone only if nothing changed after them.
    • Backups before migrationsA database dump is taken automatically before any schema update runs.

    ◎ Multi-layered caching

    • PHP OPcacheCompiled PHP stays in memory instead of being re-read on every request.
    • Compiled views & eventsTemplates and event maps are pre-built at startup.
    • Application cacheExpensive results (like the assistant’s search index) are built once and reused.
    • Browser cachingGame assets cached by the browser for a day; sensitive pages marked no-store on purpose.

    ⛨ Traffic control & security

    • Rate limiting (throttle)Per-route limits, e.g. 5/min on sign-up and password reset, 3/min on code resends.
    • Progressive lockoutRepeated wrong logins wait longer each time: 1 min, 5 min, then 15 min.
    • OTP · encrypted columns · RBACOne-time login codes, encrypted secrets in the database, role-based access.
    • Session hardeningIdle sign-out, CSRF protection, sign-out everywhere after a password change.
    • Security headers · least privilegeAnti-clickjacking headers, a dedicated limited database account, database reachable only from the host PC.

    ✓ Testing & quality

    • ~500 PHPUnit feature testsRun on an in-memory database, so the whole suite runs safely in minutes.
    • Frozen-clock testsDate rules (cut-offs, monthly periods) are tested at fixed moments in time.
    • Staging databaseRisky changes are tried on a copy of the real data first.
    • Regression testsFixes come with a test that proves the bug stays fixed.

    ▣ Documents & reporting

    • DOCX / XLSX templatingFills the office’s original Word and Excel templates by editing their XML, keeping every layout, style and image.
    • PDF & Excel exportsDomPDF and OpenSpout for printable and spreadsheet outputs.
    • Same output in PHP and RustThe Rust version was checked to produce documents identical to the PHP one.
    • Rule-based assistantAn in-app helper that understands English and Filipino questions and answers them from the database.

    ⚙ DevOps & deployment

    • One-file PowerShell launchersInstall everything, pull updates from GitHub, and start every service with one double-click.
    • Self-healing setupCreates the database, its own DB account and settings; keeps the app key safe across reinstalls.
    • Atomic config writesSettings files are written to a temp file and swapped in, so they’re never left half-written.
    • Android build pipelineRust cross-compiled with the Android NDK, packaged with Gradle into a signed APK.
